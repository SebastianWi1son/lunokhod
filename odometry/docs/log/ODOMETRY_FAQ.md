## 0. 一次 `update()` 的全景（先看这张图）

```
每 10 毫秒，上层调用一次：
        odom.update(twist, dt, tick, cmd, ws)
                 │
   ┌─────────────┴───────────────────────────────────────┐
   │  喂进来的东西（5 个参数）                              │
   ├─────────────────────────────────────────────────────┤
   │  twist (Twist)     这 10ms 里车真实的速度  vx,vy,wz   │
   │  dt    (float)     过了多久 = 0.01 秒                 │
   │  tick  (uint32)    现在几点（自增计数，单位你定）      │
   │  cmd   (Twist)     上层"想让"车跑的速度（期望值）      │
   │  ws    (指针)      四个轮子的原始转速（只作记录）       │
   └─────────────┬───────────────────────────────────────┘
                 │
   ┌─────────────┴───────────────────────────────────────┐
   │  里面干三件事                                         │
   ├─────────────────────────────────────────────────────┤
   │  ① 用 twist 把位姿往前推一步   → pose 变了            │
   │  ② 把这一帧的输入 + 新位姿打包 → OdometrySample       │
   │  ③ 装了 sink 就把它丢出去                             │
   └─────────────┬───────────────────────────────────────┘
                 │
        返回值 = 新的 pose（车现在在哪、头朝哪）
```

**参数分两类（这条是第一遍读代码最容易混的）：**

| 类别 | 字段 |
|---|---|
| **参与计算** | `body_vel`（速度）、`dt`（间隔） |
| **只作记录** | `tick`、`cmd`、`ws` |

## 2. 两个最容易糊的概念

### 2.1 为什么 yaw 要两个出口？

车原地转 **3 圈**，内部记的数字是 `18.85` 弧度（= 6π）。

```
yaw_continuous()  →  18.85     ← 融合层要这个
pose().yaw_       →   0.00     ← 导航层要这个（18.85 − 3×2π）
```

- **融合层要连续的**：给折过的值，车头从 179° 转到 −179° 时，它会以为"车突然反向转了 358°"，融合会炸。
- **导航层要折过的**：它只关心"朝哪"，不想自己折。

**内部只记一个连续值，出口时再折** —— 不是记两份。

### 2.2 为什么 `twist_scale` 要乘三个通道，不能只乘 vx、vy？

轮径误差是**均匀放大**的。轮子大 3%：

- 前进速度算小 3% → `vx` 要乘
- 横移速度算小 3% → `vy` 要乘
- **转角速度也算小 3%**（`wz = (vR − vL)/轮距`，两轮都小 3%，差也小 3%）→ `wz` 也要乘

漏了 `wz`：车实际转 360°，里程计只记 349° —— **每圈丢 11°**。

## 3. 问题与解答

### [2026-09-13] Q1：`tick` 的意义是什么？为什么不直接累加 `dt`？

**答：**

关键认知：**在 odometry 里 `tick` 不参与积分。** 它和 `cmd`、`ws` 是同一种东西 —— 塞进样本给外面用的，不影响积分结果。

为什么不内部累加 `dt`：

1. **组件零依赖，不能自己看表。** 设计限制只 include `<cmath>`/`<cstdint>`，不能 include `<chrono>`。所以"现在几点"必须由调用方给 —— 而 STM32 的 `HAL_GetTick()` 正好免费返回 `uint32_t` 毫秒数。`tick` 是硬件白送的。
2. **记录要的是「时刻」，不是「间隔」。** 写 CSV 要的是"第 1230 毫秒的一帧"。自己累加 `dt` 能得到近似时刻，但那是浮点累加，会漂；`tick` 是绝对量，永远能重算。
3. **能查丢帧。** `tick` 从 100 跳到 130，你知道中间少了 3 帧；`dt` 看不出来（丢帧时它的值也丢了）。

关联：`../../control/wheel/docs/log/WHEEL_LESSONS.md` 沉淀过「**dt 是实测值，不是配置值**」——
`tick` 就是让 `dt` 能被**实测**出来的东西：`dt = (tick − last_tick) × 0.001`。

### [2026-09-13] Q2：与其说在做里程计，不如说是"轨迹记录计"（PoseRecord）？

**答：** 主职是**积分器**，记录是**附赠的黑匣子**（`sink = nullptr` 时一帧都不记）。

**但这个直觉抓到了真东西** —— 组件确实背了两个职责，设计 §1「一个数据源，三个出口」就是在承认它。

记录为什么必须放在这一层：

> **这里是「轮速 / 指令 / 实际体速度 / 位姿 / 时间」唯一同时在场的地方。**

- 往上（导航）：只有 pose，看不到轮速
- 往下（wheel）：只有轮速，看不到 pose
- 打滑检测（`cmd` 期望 vs `twist` 实际）和系统辨识，必须在两者交汇处取数据

结论：名字不改（`odometry` 是行业标准词），但形态是「**积分器 + 可选黑匣子**」。

### [2026-09-13] Q3：能不能用 `rotation_record` + `abs_yaw = rotation_record + raw_yaw`（跳变检测）？

**答：** 你的做法是对的，它叫 **角度解缠（angle unwrapping）**，是编码器 / IMU 的标准套路
（`numpy.unwrap` 干的就是这件事）。

**但它解决的是另一个问题：还原一个"已经被折过"的信号。**

odometry 是**自己积分出来的**，源头没折过：

```cpp
yaw_ += wz * dt;   // wz 是【角速度】，不是角度
```

角速度没有"折"的概念（"0.5 rad/s" 不是 "355°"）。我们只是不停往上加，加出多少就是多少 → **天然连续**。

| | 解缠（你的做法） | 不折（odometry 的做法） |
|---|---|---|
| 输入 | **已经折过的角度**（如四元数转出的 Euler） | **角速度** `wz` |
| 要做什么 | 检测跳变 → 补圈数 | 什么都不用做，直接加 |
| 弱点 | 阈值 `0.8` 是魔法数；两次采样之间真的转了很多时，分不清"转得多"还是"跨了圈" | 无阈值，只有积分本身的误差 |

**你什么时候会用到解缠**：从 **foucault 的四元数**里取 yaw 时 —— `to_euler()` 出来的永远是折过的。
那是**消费方**的活，不是里程计的活。设计 R2 选"两个明确出口"而非"计数器 + 阈值"，就是为了避开魔法数。

### [2026-09-13] Q4：`reset()` 到底保留什么？样本打包那一段在干什么？

**答 (a) `reset()`：**

```cpp
void reset() { x_ = 0.0f; y_ = 0.0f; yaw_ = 0.0f; }   // 只清这三个
// twist_scale_、sink_、sink_ctx_ 一个字都不动
```

**一句话：`reset()` 清的是「状态」，不是「配置」。**

- `reset()` 语义是"**把车现在的位置当新原点**"，不是"恢复出厂设置"
- `twist_scale_` 是**硬件属性**（轮子半径），与"车现在在哪"无关 → 重对位不该清标定
- `sink_` 是**接线**，与位姿无关 → 重对位不该拔线

**类比（自己验证一下对不对）**：`wheel` 的 `reset()` 会清 PID 积分项，但**不会把 `kp_` 改成 0**。

**答 (b) 打包：**

```cpp
if (sink_ != nullptr && ws != nullptr) {
    const OdometrySample smp{tick, dt, *ws, cmd, Twist{vx, vy, wz}, p};
    sink_(sink_ctx_, smp);
}
```

| 片段 | 意思 |
|---|---|
| `sink_ != nullptr` | 没装出口 → 没人要数据，不记 |
| `ws != nullptr` | 调用方没给轮速 → **宁可丢帧，不写脏数据**（R7） |
| `OdometrySample smp{...}` | 花括号一次填满 6 个字段（**聚合初始化**，STAGE1 学过） |
| `*ws` | 把指针"解开"取出真正的 `WheelSpeeds` —— **拷一份**，不是存指针 |
| `sink_(sink_ctx_, smp)` | 调用注册的函数，第一个参数是那份"行李"（ctx） |

两个容易想漏的点：

1. **为什么在积分之后？** 样本里的 `pose_` 必须是**这一帧算完的**位姿；放积分前会记成上一帧的，记录和积分差一帧。
2. **为什么 `*ws` 要拷贝？** 只存指针的话，调用方那个对象一改或一销毁，记录里就是悬空垃圾。

### [2026-09-13] Q6：第一次手敲完成 —— 三个坑分别是怎么被发现的？

**结果**：原样编译失败 → 改完 3 处后 **113/113 全绿**。

| 坑 | 性质 | 谁发现的 |
|---|---|---|
| `twist_cmd_` vs 契约的 `cmd_` | 契约不同步 | **编译器**（字段名不存在） |
| `y_ += (vx*s + vy*s)*dt`（应为 `vy*c`） | 逻辑错 | **测试 [1][2]**（3 条 FAIL） |
| struct 里 `twist_` / `cmd_` 顺序与设计相反 | 静默错位 | **测试 [9] sink 记录**（2 条 FAIL） |

#### 为什么第 3 个最危险

`cmd_` 和 `twist_` 是**同一个类型** `Twist`，聚合初始化按**位置**匹配 ——
类型对得上就通过，**编译器没有任何办法知道你“想装哪个”**。

结果：`twist_` 装进了 cmd 的值，`cmd_` 装进了实际 twist 的值 —— **两个值静默对调**。

**数学测试全绿**（因为数学确实是对的），只有 [9] 抓住：

```cpp
CHECK(abs_diff(rec.last_cmd_vx,   0.5f) <= 1e-6f);   // 期望 → 拿到 0.4  ✗
CHECK(abs_diff(rec.last_twist_wz, 0.2f) <= 1e-6f);   // 实际 → 拿到 0.25 ✗
```

**如果当初把 [9] 当成“次要测试”删掉，这个 bug 会一路带到真机上** —— 打滑检测会拿到对调后的数据。

#### 为什么第 2 个难自己看出来

```
yaw = 0 时：s = 0，c = 1
    vy*s = 0      vy*c = vy
    → 如果同时 vy = 0（直行），两者都是 0，完全一样
```

只有 **vy≠0 且 yaw≠0** 时才暴露 → 靠 [1] `circle` 和 [2] `mecanum_slide`（vy=0.4, wz=0.5）揪出来。

1. 相邻同类型字段要么顺序对齐契约，要么加一条“谁装进谁”的测试
2. **字段名是契约**；契约的源在设计文档，改契约先改设计再同步测试与代码
3. 写旋转矩阵必须有一条 vy≠0 且 yaw≠0 的用例

### [2026-09-13] Q5：`pose` 获取 和 打滑检测 的最小原理？内部能不能解耦？

**A（pose 获取）：** 一句话 —— **把“速度×时间”一步步加到坐标上，方向用当前朝向旋转。**

```
yaw += wz·dt                                ① 朝向变了多少
x   += (vx·cos yaw − vy·sin yaw)·dt         ② 前进量 → 世界 x
y   += (vx·sin yaw + vy·cos yaw)·dt         ③ 前进量 → 世界 y
```

**关键认知：它没有任何纪正机制，它只是加法。** 所以误差**只会累积，不会自愈** ——
这是“航位推算（dead reckoning）”的**定义**，不是 bug。

因此里程计的输出永远是**条件参考**：“**如果**没打滑、**如果**模型准，车应该在这。”

**A（打滑检测）：** 一句话 —— **两把独立的尺子量同一件事，对不上就是有问题。**

关键在“独立”：两条信号链必须来源不同。两条都从轮子来，就检不出轮子自己的错。

| 级别 | 比什么 | 需要硬件 | 能抓什么 |
|---|---|---|---|
| **0** | `cmd`（期望） vs `twist`（实际） | 只要编码器 | 严重打滑 / 堵转 / 电机没跟上 |
| **1** | 里程计 Δyaw vs **陀螺** Δyaw | + 陀螺 | **单边打滑**（原地打转、差速甩尾） |
| **2** | 里程计位移 vs 加速度计短时积分位移 | + 加速度计 | 直线打滑 |

Level 0 最小实现（不需额外硬件）：

```
每帧：
    如果 (twist.vx < cmd.vx × 0.5) 且 已持续 0.3 秒：
        报“疑似打滑 / 堵转”
```

**Level 0 的局限**：对不上**不一定**是打滑，也可能是电机力不够、PID 没调好、或正在加减速。
所以 Level 0 只能给“**可疑**”信号，**定论要靠 Level 1/2**（IMU 当参照）。

**A（能不能解耦）：** 要分清解耦**哪一对**。odometry 内部有三个关注点：

```
├── x_, y_, yaw_        ← ① 积分（pose 获取）
├── twist_scale_        ← ② 标定
├── sink_, sink_ctx_    ← ③ 记录
└── update() = ① + ② + ③
```

- **打滑检测是第 ④ 件事，它根本不在里面** —— odometry 只**输出数据**，不**下判定**。
  判定一旦进来就要依赖 IMU，会从“底盘无关”变成“绑死硬件”。**这对已经解耦了。**
- **积分 vs 记录：v1 故意绑在一起**，三个理由（时序一致性 / 样本里 `twist_` 是标定后的值 /
  `sink==nullptr` 时零成本）。真要拆得新开 `last_twist()` 公开口 —— **公开 API 扩了收不回来**。
  结论记在 `../ODOMETRY_DESIGN.md` §7b R13；**触发重开讨论的条件**：出现第二个需要记录的组件。

判据：**解耦的价值 = 两件事的“变化原因”不同**。积分因“算法改进”而变，记录因“字段/协议”而变，
确实不同；但“现在只有一个消费者”压倒了一切 —— 拆了是在为想象中的第二个消费者付成本。
